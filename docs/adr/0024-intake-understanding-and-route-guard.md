# ADR-0024：接待改为「轮次理解 → 路由守卫」，拿不准先提议；运行页只把补充要求记为备注

- 状态：Accepted
- 日期：2026-10-02
- 关联：ADR-0016（服务端托管对话轮）、ADR-0018 / ADR-0020（对话即控制面；本 ADR 修订 ADR-0020 §1「没有动作、也不是问句的话落成运行备注」）、[前后端与 Agent 对接日志](../development/frontend-backend-agent-integration.md)

## 背景

首页发送先过接待判定（`POST /v1/task-intake`），判成 `modeling_task` 就建项目、起六阶段。v1 的判定原则是「拿不准一律放行，误放由问题分析节点的 viability 门兜底」，于是：

- 赛题标识优先于问句：「美赛和国赛有什么区别」「数模论文的摘要一般怎么写」直接建任务；
- 正文 ≥200 字即放行：长篇提问被当成题面；
- 附件 = 开始建模：解析不出文字的附件一律放行，有摘录时提示词写「含题面或数据说明即为 modeling_task」；
- 判定看不到对话历史：首页对话里的「好的，开始吧」「就用刚才那个数据做预测」孤立判定，放行时 goal 只剩这一句，题面全丢；
- 判定失败 / 解析失败一律放行；未配置接口时发一句「你好」也建项目跑模拟链；
- 接待结论没告诉对话模型：判「缺信息」时模型可能答「好的我来建模」，然后什么都不会发生；首页对话也根本不带附件，「分析文件」没有通路。

运行页（ADR-0018 / 0020）的判定只回答「是不是动作」，不触发动作、又不像问句的话一律记成运行备注注入后续所有节点：「谢谢」「太慢了吧」「这个模型的精度多少」、甚至在运行页贴一道新题，都会进节点提示词。

2026-10-02 用户要求把「意图 / 是否要求执行 / 是否需要建模 / 事件 / 会话状态 / 续接还是新任务 / 言语行为 / 题型 / 缺失信息 / 把握 / 路由」作为整体修复，并拍板三处策略：拿不准时**先提议、确认再启动**；首页确认形态是**对话里回一句**（零界面改动）；未配置接口时**本地规则照样拦**。

## 决策

### 1. 接待分两层：理解是结构化的，路由是确定性的

`intake.py` 先读本地信号（赛题标识、任务型信号、问句、知识型问句、请求 / 执行措辞、寒暄、光秃秃的「开始」、指代上文、修改措辞、附件指代、题型），能定的不出网；拿不准的交池中最弱模型做一次限时 JSON 判定，判定只输出结构字段——`intent`（modeling_task / needs_info / knowledge / file_analysis / chat）、`execution`、`continuation`、`domain`、`missing`、`confidence`——不再写回复。

`route`（start / propose / clarify / reply）只由规则给出，顺序为：

1. 上一轮有待确认的提议：确认（「好的，开始吧」「可以，不过目标改成成本最小」）→ start，goal = 提议记下的题面（附带的新要求接在「补充要求：」后）；拒绝（「先不用了」「好，但先别开始」）→ reply；其它 → 提议作废、按新话判。
2. 寒暄与极短输入本地处理；带赛题标识 / 请求措辞的极短输入（「A题」「帮我建模」）→ clarify。
3. 未配置接口：寒暄 / 明显问句 / 只传文件不说要做什么 → reply；改提议 → 再提议；其余 → start（演示链路）。
4. 已配置接口的本地强证据：长题面 + 执行措辞、不是知识问句 → start；明确的知识问句 → reply；附件内容不可见时按话语定（要求按附件建模 → start，「题目见附件」→ propose，问文件 → reply）。
5. 判定结论：modeling_task 缺题面且没有附件 / 上文 → clarify；明确要求开始且把握 ≥0.6、不缺求解目标 → start；否则 propose。needs_info 在本地看得到对象与目标（任务型信号、非问句）时不拦人：要求动手 → start，没说 → propose（v1 的否决语义按提议策略收窄）；否则 clarify。knowledge / file_analysis / chat → reply。
6. 判定失败 / 输出无法解析：执行措辞 + 任务信号 / 题面 / 附件 → start；题面形态 → propose；要动手却看不出做什么 → clarify；其余 → reply。

**附件永不单独构成 start**：上传文件、@ 引用资料只是证据。问句判断按长度分档——60 字以内任何问句标记都算，更长的文本只认句首发问与句尾问号，题面里的「是否 / 多少 / 如何」不算问句。

### 2. 契约向后兼容地扩展

- `TaskIntakeInput` 新增 `history[{role,text}]`（≤12 条首页对话原话）、`pending_task{goal,domain}`、`confirmed`（确认页点了「开始任务」）。
- `TaskIntakeResult` 新增 `route`、`understanding{kind, speech_act, execution, requires_modeling, continuation, domain, missing, confidence}`、`task_goal`、`context_excerpt`、`chat_ready`；`intent` 保留旧三值并与 route 对齐（start → modeling_task，propose / clarify → needs_info，reply → chat），只认 intent 的旧前端照常工作。`reply` 改为模板回应（确认页状态行、未配置接口时的首页回应）。
- `ChatRequest.intake{route, kind, speech_act, domain, missing, task_goal}`：首页对话轮换用首页系统提示词（不得自称已开始建模）并注入【接待判定】块；托管轮的首个 `meta` 事件带 `intake`，落 `meta.intake`。任务页（`run_…`）的轮忽略它。

### 3. 首页：对话与路由对齐，确认在对话里完成

- 前端记着首页对话的原话与上一轮提议，随每次接待判定上送；提议落在该轮 `meta.intake`，刷新或从侧栏重进后从最后一轮恢复——下一句「开始」照样有所指。
- route=start 时 goal 用 `task_goal`（确认提议时是提议的题面，指代上文时由上文拼出），`context_excerpt` 作为 `params.conversation_context` 随任务创建，问题分析节点的附件摘要段把它排在最前、单独封顶 1500 字；两者写进草稿，后续步骤失败重试时不再过判定也保得住题面。
- 其余路由进首页对话：接待结论随轮上送；托盘里还没注入过的附件正文随这一轮送给模型（每个附件只注入一次，托盘保留作后续任务材料），首页对话从此能「分析文件」。
- `chat_ready=false`（未配置接口）时首页不发起对话轮，接待的模板回应就是这一轮的回复。

### 4. 运行页：不触发动作的话先分类，只有补充要求才记为备注

判定 JSON 增加 `utterance`（supplement / question / feedback / chat / new_task），只有 supplement 落备注。判定缺席（未配置、判定失败、输出无法解析）时本地兜底：运行页贴来的新题、情绪反馈短句、问句（问句标记补上「怎么 / 多少 / 什么」等）、寒暄致谢都不进备注，其余维持旧行为记为补充要求——宁可多记一条，也不吞掉用户真正的要求。超过 800 字的粘贴仍不送动作判定，但会做一次「只分类、不触发动作」的判定（提示词带本任务题面），把「另一道新题」挡在备注之外。new_task 在状态块里告诉模型：不会记为本任务的补充要求，请用户回首页新建。

执行安全不变：合法动作集、不可逆动作先提案、回复结束后才执行（ADR-0020）。

### 5. 明确不做

- 不新增确认按钮或卡片：确认在对话里回一句即可（用户拍板，零界面改动）；
- 不让模型在回复里直接决定路由：判定只给结构字段，路由由规则定，模型的回复只负责与路由对齐；
- 不改 `POST /v1/task-runs`：直接调用方跳过接待仍属合法用法，题面无效时由问题分析节点的 viability 门兜底；
- 不改受保护入口、页面模板与路由。

## 结果

- 「美赛和国赛有什么区别」「这张图是什么意思」「看看」+ PDF、「你好」（未配置）都不再建项目；只描述题目、没说要开始时先在首页对话里复述并提议，回一句「开始」才启动，goal 是完整题面而不是「开始」二字。
- 粘贴的完整赛题（题面 + 「请建立模型」）仍一步直达、不烧判定调用；有对象有目标的一句话需求不会因为「描述太简略」被拦。
- 首页对话的回复与路由一致：提议时模型复述题意并问是否开始，缺信息时说清缺什么，问知识时直接回答。
- 运行页的「谢谢」「太慢了吧」「精度多少」不再注入后续节点；贴来的新题不污染当前任务。
- 代价：寒暄、明确的知识问句、长题面、确认 / 拒绝提议不出网；其余仍是一次 ≤10 s 的最弱模型判定（与 v1 相同）。超长粘贴在运行页多一次只分类的判定。
