# ADR-0020：对话控制动作在回复结束后执行；词表只作参考信号、不再单独触发

- 状态：Accepted
- 日期：2026-09-08
- 关联：ADR-0016（服务端托管对话轮）、ADR-0018（对话即控制面；本 ADR 修订其 §1「生成之前执行」与 §3 的事件顺序）、ADR-0019（判定以模型为主、规则为快路径；本 ADR 修订其 §4 的短句快路径与「模型 none 回落规则」）、[前后端与 Agent 对接日志](../development/frontend-backend-agent-integration.md)

## 背景

ADR-0018 把控制步骤放在托管轮 **调用模型之前**：判定 → 立刻执行 → 把「已执行的操作」注入系统提示词 → 再生成回复。ADR-0019 又把判定做成「短句（规范化后 ≤12 字）命中词表即直判、不出网；长句交判定模型，模型说 `none` 时回落到词表命中的结果」。

2026-09-08 用户实测（运行在「实验运行」阶段失败后，在聊天框里发了一句带「重试」字样的话）看到的是：模型还在「思考中」，下方的执行步骤区就已经出现并开始滚动（`ws_list` / `env_probe` / 深度思考·实验执行），回复随后才姗姗说「已按你的指令重试当前阶段」。用户裁定两条：

1. **「我要的效果是模型回答完了之后，再出现下面这些执行的，而不是在思考中直接就开始执行。」** 对话和它触发的动作应当是一个连贯的先后：先把话说完，再动手，执行步骤随后才长出来。
2. **「有关键字了就直接触发重新执行，这肯定是不行的啊，要结合在一起的。」** 词表命中不能单独构成执行的依据；理解这句话是不是命令，要结合上下文由模型来判，判定和回复是一体的。

## 决策

### 1. 托管轮分两步经过控制面：回复前只计划，回复后才执行

`routers/chat.py` 的 producer 在调用模型前只做 **计划**（`run_control.plan_control_step`）：读运行状态、算合法动作集、判定意图，把「回复结束后将执行什么」写进注入系统提示词的状态块。这一步**不改运行状态、不写库、不发事件**。

回复流完（上游给出 `done` / `error`，或流静默结束、生成线程异常）之后、轮定格之前，`ChatTurnHub` 调用新增的 `before_finish` 钩子——控制面在这里 **执行**（`run_control.execute_control_plan`）：

- 重新读一遍运行状态（回复要生成几秒到几十秒，期间用户可能点了按钮、运行可能自己走到了别的状态），计划里的动作不再合法（或待审批门已换）时如实回一条 `action{status:"rejected", code:"RUN_STATE_CHANGED"}`，**绝不按过期快照硬执行**；
- 仍合法则走与按钮相同的既有路径执行（`actions.execute_action` / `accept_revision` / `redo_run` / 运行备注），回执以 `action` 事件发出；
- 提案（取消 / 重做）与放弃（`dismissed`）不改状态，计划阶段就已定型，同样在回复结束后才发出——用户先看到代价说明，再看到「等待你确认操作」那一行；
- 没有动作、也不是问句的补充要求，在这里落成运行备注（此前是回复前落）。

事件顺序因此固定为：`meta` → 全部 `reasoning` / `delta` → 零到多个 `action` → 终态。页面上：回复正文 → 动作回执行 → 工作台重接事件流、执行步骤区在回复块里长出来。

**回复模型出错也照样执行**：用户的命令不该因为聊天模型抖了一下就丢掉，回执排在错误终态之前。

**用户 stop（暂停生成）= 打断了这一轮**：`before_finish` 只在轮仍是 running 时调用，被打断的轮不执行任何动作、不落备注、不发回执；再说一次即可。这是有意的取舍——「停下」时用户的意图不明，宁可少做。

### 2. 提示词改成将来时

状态块按 **执行前** 的状态写（失败运行仍写「执行失败」），动作条目标「将在你回复结束后执行：重试「实验运行」阶段，并把用户这句话作为备注注入该阶段的执行提示词」。四档回复口径（`reply_rules`）全部改为将来时，并明令不得说「已重试」「已选择」这类完成时；交接口径改为「你的回复一结束，系统就会执行上面列出的动作、由运行接手……进度随后会出现在下方的执行步骤里」。不触发动作但会落备注的一轮，状态块写「无动作；这句话会在你回复结束后记为运行备注……只是记录下来，不是已经修改」。

### 3. 判定：词表只产生候选、作为参考信号交给判定模型

`decide` 的顺序改为：

1. 上一轮留有待确认提案 → 只看确认 / 否定词（不出网）。那是在回答系统自己提出的是非题，不存在理解歧义；
2. 其余一律送判定模型（有配置的接口、有合法动作、文本 ≤800 字）。本地词表的命中结果随判定提示词一起下发为一行「参考信号：本地词表在这句话里匹配到动作 retry……词表匹配不等于用户在下命令——如果这句话只是在提问、讨论、表达情绪或提供信息，即使命中词表也返回 none」；
3. 模型说什么就是什么：说 `none` 就是普通对话，词表命中也**不回落执行**；判定异常、结果不在合法集内同样是 `none`。

删掉的：`RULE_FAST_PATH_MAX_CHARS` 短句快路径；「模型 none / 出错 → 回落规则结果」；「没有判定器时规则结果即最终结果」（没有判定器 = 未配置接口，此时对话本身也发不出去）。保留的红线不变：结果必须在合法集内、`redo` 必须带合法阶段、不可逆 / 要花钱的动作先提案。

代价如实说明：短句现在也要出一次网（≤10 s 限时、最弱模型、按 `route` 记账），「重试」两个字从发出到回复开始多了约一到三秒；换来的是不会再有任何一句话因为碰巧含了词表词就把运行重启。

### 4. 页面收口

- `agent-chat.ts` 的 `onAction` 语义改为「晚于全部正文、早于终态」；
- 回复呈现器把回执行追加在生成行**之后**（此前插在之前），并攒在 `tailRows` 里、在「已生成回复」落定之后再接进轨迹日志——轨迹日志顺序与页面一致，刷新重建不会把「已重试」排到「已生成回复」前面；
- 受保护入口、路由、`/actions` 与工作台契约零改动；`run-control-view.ts` 纯函数不变。

### 5. 明确不做

- 不让回复模型在正文里输出机器指令来「顺手」执行动作（工具遵循度参差，ADR-0018 §5 第一条不变）：判定仍是独立的一次限时 JSON 判定，只是从「执行前」变成「计划」；
- 不做 stop 后补执行：被打断的轮不猜用户想不想继续；
- 不改 `/actions`、闸门与引擎状态矩阵。

## 结果

- 用户看到的顺序变成：回复说完 → 「已重试阶段 · 实验运行」回执行 → 执行步骤开始滚动；回复里不再有「已按你的指令重试」这种在动作发生之前就说出来的完成时。
- 「重试过几次了？」「不要急着重试，先看看原因」这类带词的话不会再触发任何动作——判定模型带着上下文拍板。
- 回复期间运行状态变了（用户点了按钮）不会被对话再执行一遍，回执如实写「回复期间运行状态已变为「执行中」，「重试阶段」不再适用」。
- ADR-0018 §1「生成之前执行」与 §3「`action` 在 `meta` 之前」、ADR-0019 §4 步骤 2 与步骤 4 由本 ADR 修订。
