# ADR-0018：对话即控制面——任务页聊天框能真正驱动运行

- 状态：Accepted（§1 的判定分级、§2「失败运行不能选起点重做」与 §5「不在 RUNNING 时回退阶段 / 不改引擎状态矩阵」已由 ADR-0019 修订；§1「生成之前执行」与 §3「`action` 在 `meta` 之前」已由 ADR-0020 修订——动作改为回复结束后执行，`action` 排在全部正文之后、终态之前）
- 日期：2026-09-06
- 关联：ADR-0013（终态可返工）、ADR-0016（服务端托管对话轮）、ADR-0019（任意状态从阶段重做、判定以模型为主）、ADR-0020（回复后执行、词表不再单独触发）、[前后端与 Agent 对接日志 §5.6 / §5.8](../development/frontend-backend-agent-integration.md)、智能体设计文档 §11.3（本 ADR 修订其决策）

## 背景

任务页的聊天框此前是一个**解说员**：模型对运行状态一无所知，也没有任何执行权。

1. **看不见状态。** 托管轮的系统提示词只有身份与输出习惯一句（`routers/chat.py` `CHAT_SYSTEM_PROMPT`），`_prepare_call` 不读运行、步骤、审批任何一张表。运行刚在「实验运行」阶段失败，模型仍不知道，只能泛泛作答。
2. **没有执行权。** 前端发消息前唯一的副作用是往 `POST /task-runs/{id}/notes` 落一条运行备注（下次节点执行时注入提示词，纯被动）；运行到终态时 409 `RUN_FINISHED`，前端只能标「任务已结束，本条按问答处理」，并挂一个「按这条要求继续修改」按钮——对失败的运行点了会撞 `RUN_NOT_COMPLETED`（修订只接受 COMPLETED），是一条死路。
3. **这是当年的明确决策，不是疏漏。** 设计文档 §11.3 在「A 运行备注 / B 触发重规划 / C 转决策卡」三候选里选了 A，并写死「重做由人显式操作，绝不由备注文本触发」（`task_runs.post_run_note` docstring）。

2026-09-06 用户实测（运行 FAILED 后连发「怎么又失败了，快继续想办法」「继续啊」，得到的只是聊天）后裁定：**对话应当随时随地能驱动运行**——按钮能做的，说一句话就要能做。本 ADR 推翻 §11.3 的「文本不触发动作」，把聊天框升级为控制面。

## 决策

### 1. 在托管轮里、生成之前插一段「控制步骤」，只对 `run_…` 归属生效

`POST /api/chat/turns` 的 producer 在调用模型前依次做：

1. **读运行状态**（status / 当前阶段 / 失败原因 / 待审批门及其选项 / 修订轮数）并算出**当前状态下合法的动作集**——判据就是 `actions.py` 与 ADR-0013 的状态机规则，不另起一套；
2. **两级意图判定**：先本地规则（不出网、确定性），拿不准且文本不超过 200 字时再用接口池里最弱的模型做一次 ≤10 s 的 JSON 判定（沿用 `intake.py` 的套路）；判定异常、解析失败、结果不在合法集内，一律回落为普通对话——**绝不误执行**；
3. **执行**：走 `actions.execute_action` / 修订受理 / 备注落库这三条**既有代码路径**，同一把 `lock_run`、同一事务——「不自创动作端点」（§11.1）继续成立，对话只是第二个调用方；
4. 在事件流里先发一个 `action` 事件（见 §3），再把【当前运行状态】与【本轮已执行的操作】两块注入系统提示词，最后照常流式生成回复。模型从此知道自己刚做了什么、下一步等什么；没命中动作时也能如实告诉用户「可以直接说『重试』」。

意图判定与执行都在托管轮的后台线程里进行，建轮请求仍是 202 即返回；判定用量按 `route` 口径记账。

### 2. 分级执行：直接做的、要确认的、做不到的

| 运行状态 | 对话直接执行 | 先确认再执行 | 举例 |
|---|---|---|---|
| FAILED | `retry`，并把这句话落成 global 备注**同一事务提交**——重跑的节点提示词里带着用户的要求，不是原样再跑一遍 | — | 「继续啊」「再试一次」「换个思路重跑」 |
| WAITING_APPROVAL | `approve` 指定选项（能对上唯一一个选项时）；`reject` 退回 | — | 「用方案 B」「同意」「采用清洗结果」「退回重做」 |
| PAUSED | `resume` | — | 「恢复」「继续跑」 |
| RUNNING / QUEUED | `pause`；其余文本 = 备注（静默落库，行为与此前一致） | — | 「先停一下」「把目标函数改成加权成本」 |
| COMPLETED | 发起修订（ADR-0013）：正文点名了阶段时把该阶段设为推荐项并预选，修订门照开；随后一句「确认」或点门上的按钮即重跑 | — | 「把论文摘要改短」「从数据准备重做」 |
| 任意非终态 | — | `cancel`：先发提案，回「确认」或点按钮才执行 | 「取消任务」「别跑了」 |
| CANCELLED | 无可执行动作，如实说明 | — | — |

- **确认的形态**：需确认的动作先发 `action{status:"proposed"}`，前端渲染一行带按钮的轨迹行（复用 `.stream-cta`），按钮等价于以「确认」发一条对话；下一轮判定器**先看上一轮**是否留有待确认提案——「确认 / 是 / 好 / 可以」执行，「不 / 算了 / 取消 / 不要」作废，其它文本视为放弃提案、按新意图处理。提案只对紧接着的下一轮有效。
- **修订门为什么还开**：从问题分析重做与从论文撰写重做花费差一个数量级，ADR-0013 把「选定起点」定为必要的知情同意；本 ADR 只把用户点名的阶段变成推荐项 + 预选，让确认从「在门里挑选」缩成「说一声确认」。对话里说「确认」同样经 `approve` 走 `/actions` 那条路径解决这道门。
- **失败运行不能选起点重做**：引擎的 FAILED 只有 `retry`（重跑当前失败阶段），修订门只接受 COMPLETED。本 ADR 不改状态矩阵；「失败运行也能从更早阶段重做」作为后续独立一刀（引擎加 `FAILED → NEEDS_REVIEW` 出边）。
- **问句不算命令**：「为什么失败了」「怎么回事」交给模型回答（带着状态块，它答得出来）；一句话同时带问句与命令（「怎么又失败了，快继续想办法」）按命令处理——动作先执行，回复里顺带解释原因。
- **备注保持静默**：用户 2026-09-04 已明确撤掉「已同步给执行中的智能体」样板行；只有真实动作才渲染轨迹行。

### 3. 事件与视图契约

托管轮事件流在 `meta` 之前可出现零到多个 `action` 事件：

```json
{"type":"action","seq":1,"kind":"retry","status":"executed","stage":"EXPERIMENTING","stage_label":"实验运行","message":"已重试「实验运行」阶段，并把你的要求作为备注注入该阶段","note_id":"note_…"}
{"type":"action","seq":1,"kind":"cancel","status":"proposed","message":"要取消这个任务吗？取消后不可恢复。","confirm_hint":"回复「确认」或点下方按钮执行"}
{"type":"action","seq":1,"kind":"approve","status":"executed","approval_id":"appr_…","option_id":"adopt:plan_b","option_label":"方案 B：…"}
{"type":"action","seq":1,"kind":"revision","status":"executed","round":1,"approval_id":"appr_…","stage":"DATA_PREPARATION","stage_label":"数据准备"}
{"type":"action","seq":1,"kind":"retry","status":"rejected","message":"当前运行不在失败状态，没有可重试的阶段"}
```

- `status`：`executed`（已生效）/ `proposed`（等确认）/ `rejected`（判出了意图但状态机不允许，如实告知）/ `dismissed`（上一轮的提案被用户一句「算了 / 不要」放弃，运行状态不变）。
- 事件同时并入轮视图的 `meta.actions[]`，刷新 / 重进页面时照样重建；`proposed` 且尚未被后一轮处理的提案在恢复时仍带确认按钮。
- 事件是增量通知，快照仍是页面恢复依据：动作 `executed` 后前端广播 `omm:run-reopened`，工作台控制器立刻拉快照并重接运行事件流（复用 ADR-0013 修订受理后的同一条路径）。

### 4. 前端收口

- 发消息前的 `postRunNote` 与终态 409 后的「按这条要求继续修改」按钮**整体移除**：副作用统一在服务端托管轮内发生，前端只渲染服务端说它做了什么。`offerRevisionCta` 随之退役。
- `agent-chat.ts` 新增 `onAction` 回调；`integration/run-control-view.ts` 纯函数把 `action` 事件整形成轨迹行（标题为静态可翻译文案，阶段 / 选项名走 `suffix`，与既有「标签与后缀分节点写入」的口径一致），`node --test` 直测。
- 受保护入口（`App.tsx` / `screens.tsx` / `OpenMathModelScreen.tsx`）、路由、`/actions` 与工作台契约零改动。
- **补注（2026-09-07，实机报障后）**：动作 `executed` → 重接事件流后，重跑阶段的运行事件到达时对话尾部正是这条回复块；控制器不再另起带署名的 Agent 块，而是在**同一回复块内部**（正文与复制按钮之后）挂「收起执行步骤」折叠头继续写——回复与它触发的执行步骤在页面上是一条 Agent 消息。系统提示词的回复要求随动作情形分三档（`run_control.reply_rules`）：有 retry / resume / redo / approve / reject / revision 已执行 → 交接口径，告知已做什么与运行接下来做什么，**不得在对话里替运行算题、建模或写论文**（否则聊天模型与运行节点并行解同一题）；有待确认提案 → 说明代价请用户确认；其余保持原口径。`run.log{kind:"user_note"}` 渲染为叙述行。

### 5. 明确不做

- 不给对话模型开放工具调用去自己拍板动作：五种上游协议与中转站的工具遵循度参差（intake 一路的弱模型误判是前车之鉴），动作必须由确定性的合法集校验兜底，模型只负责把意图归到枚举里。
- 不在 RUNNING 时按对话文本回退阶段（那是 G 闸门与修订门的职责）；不新增领域阶段、不改引擎状态矩阵。
- 首页对话（`chat_…` 归属）没有运行，不经过控制步骤。

## 结果

- 对话从「解说员」变成「控制面」：FAILED 说「继续」即 retry 且带上要求；WAITING_APPROVAL 说「用方案 B」即批准；COMPLETED 说「从数据准备重做」即受理修订并预选起点；任何状态下问「为什么」都能得到带真实状态的回答。
- 代价：每轮多一次读库与（拿不准时）一次弱模型判定；判定错误的最坏情形是「该做没做」（回落对话，用户再说一遍）或「做了不该做的」——后者被两道闸挡住：合法集校验 + 取消 / 跳过门的动作必须确认。
- 设计文档 §11.3 的决策由本 ADR 修订：A（备注）仍是基础通道，但 B / C 的「由人显式升级」不再限定为点按钮——对话文本经判定后可直接触发。
